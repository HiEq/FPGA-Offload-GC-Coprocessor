# 提示词工作流：软硬件划分 与 综合报告定位瓶颈

## A. 算法描述 → 软硬件划分草案

**适用**：已有算法/数据流描述，需要在 PS 软件与 PL 逻辑之间切分。
**失效条件**：算法没有稳定的数据布局或访存模式无法描述时，划分结论不可信。

提示词模板（把尖括号内容替换掉）：

```
你是 FPGA 软硬件协同设计评审。下面是一个算法与运行环境，请给出划分方案。

算法：<步骤、数据规模、循环结构>
数据布局：<每个元素多大、是否连续、读写比例>
约束：<器件型号与可用资源、时钟频率、接口带宽、延迟要求>
已有实现：<CPU/GPU/脚本的实测时间与瓶颈>

要求：
1. 按“访存密集 / 计算密集 / 控制密集”给每个阶段打标签；
2. 给出 2–3 种划分方案（全部软件 / 全部硬件 / 混合），每种写清数据搬运次数与理论下界；
3. 指出每个方案的失败条件（什么数据规模下反而不如软件）；
4. 只输出表格与结论，不要复述算法。
```

**验证方式**：把草案里的“理论下界”与实测对照；本项目用同图四路对比
（FPGA / C 未缓存 / C 缓存 / Python）验证“指针追逐受 DDR 限制时硬件才占优”。

## B. 综合报告 → 瓶颈定位

**适用**：已有 `report_utilization` / `report_timing_summary` 输出，需要定位资源或时序瓶颈。
**失效条件**：报告语言非英文或使用了自定义报告模板时，需先统一关键词。

```
下面是 Vivado 的资源与时序摘要。请：
1. 指出最可能的关键路径类别（LUT 级联 / BRAM 输出 / DSP 级联 / 跨时钟）；
2. 给出 3 条互斥的优化假设，每条写“若成立，报告中应出现什么信号”；
3. 按“改动代价 / 预期收益”排序；
4. 明确哪些结论必须回到实现报告核对，不能从摘要推断。

资源：<粘贴 utilization 表>
时序：<粘贴 WNS/WHS 与最差路径摘要>
```

**验证方式**：本项目 WNS 从 +0.123 → +0.049 的两次实现，用该流程定位到根集读回 mux 的路径，
随后由 `report_timing` 的具体路径确认。
