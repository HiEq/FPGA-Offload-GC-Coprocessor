## 1. 使用方式与边界

- 角色：人负责需求、验收口径、RTL 框架与模块接口/互联的编写、上板实测与发布决策；
  模型负责实现建议、重构、差异审查与文档整理。
- 约束：仓库内的 AGENTS.md 是协作规范，要求每次改动给出验证命令与结果、禁止用编译或综合
  代替验证、禁止为了通过而放宽测试。
- 记录边界：模型输出不构成证据。所有结论以仓库中的代码、测试、日志与发布资产为准。

## 2. 协作流程

1. 人给出目标与验收标准。
2. 模型提出改动清单与验证命令，先列清单再动手。
3. 模型实现并执行本地检查（契约测试、语法检查、负控）。
4. 人在板上执行，模型根据串口输出修正判断。
5. 双方确认后提交；提交信息必须带 verified / unverified 两行。

## 3. RTL 与主机代码案例

### 案例 1：换图时在途读数据串到下一轮

- 提示词（摘要）：换图后偶发读到上一轮的数据，或引擎挂住，定位并修复。
- 模型输出：定位到三处同拍问题并列成清单：启动门控、FIFO 弹出与丢弃门控、flush 退出条件。
- 人工修正：首轮只改启动与弹出，复测仍偶发；补上 `!ARVALID` 后消失，三个情形各补一个
  定向 testbench。
- 验证：定向 testbench 在修复前报 `stale data survived abort`、`stale beat visible`、
  `timeout after duplicate START`，修复后全部通过（负控日志 xsim_handover_neg_20261024.log）。
- 结论：指针重装、FIFO 弹出、flush 退出是同一竞态的三个方面，只改一处仍会复现。

### 案例 2：命令 FIFO 在同一拍又入队又出队

- 提示词（摘要）：换图后下一轮发出了上一轮的地址，检查命令 FIFO 的指针。
- 模型输出：定位到入队路径未门控，给出两条入队路径的修改。
- 人工修正：要求同时断言脉冲结束后写指针不变；只改出队路径仍会复现。
- 验证：未修复时 `c0r=4 c0w=5`、`c1r=0 c1w=1`；修复后 `c0r=c0w=4`、`c1r=c1w=0`；
  对应 testbench 为 sim/tb_cmdfifo_flush.v。
- 结论：脉冲类信号要同时检查“消费侧”和“生产侧”，否则队列会在复位窗口里被写脏。

### 案例 3：位图探针写入后立即读取

- 提示词（摘要）：探针偶尔读到上一个对象的标记位，检查写后读时序。
- 模型输出：给出“写地址后固定等待 2 拍、地址写后回读校验”的修复。
- 人工修正：把失败返回值定为 `0xFFFFFFFF`，并要求调用方退回全量标记，不得继续使用旧数据。
- 验证：板上 v4.6 冷启动序列 `loss=[] forged=[]`，`--verify-effect` 第 0 轮无需回退
  （tools/logs/board_regs_aww_cold_20261025_v46.log）。
- 结论：带延迟的只读寄存器必须把“等待”写进访问函数，不能依赖调用顺序。

### 案例 4：队列满时静默丢对象

- 提示词（摘要）：大图标记数偏少，但 STATUS 全为 0，排查是否有对象被丢弃。
- 模型输出：建议把溢出位粘滞并映射到 `STATUS[0]`。
- 人工修正：要求仿真用 `force q_full` 覆盖该分支，并加“去掉粘滞位必须失败”的负控。
- 验证：负控强制满队列时 `STATUS[0]=1` 且 `marked=0`；把溢出位改回常量 0，该用例失败。
- 结论：正常负载到不了的错误分支只能靠注入覆盖；没有状态位就无法区分“图小”和“丢对象”。

### 案例 5：屏障校验把探针哨兵当成“已标记”

- 提示词（摘要）：审查 barrier_verify 的实现，确认探针失败时不会误判。
- 模型输出：指出 `all(read_mark(i) for i in ids)` 把 `0xFFFFFFFF` 当真值，建议改为等于 1。
- 人工修正：要求补主机单测与板上哨兵负控；负控必须在修复前为 True、修复后为 False。
- 验证：主机单测 6 个用例（已标记、未标记、哨兵、全哨兵、空集、ID 强制转换）通过；
  板上哨兵负控：修复前返回 True，修复后返回 False
  （tools/logs/board_barrier_verify_sentinel_neg.log）。
- 结论：哨兵值必须是显式分支，不能依赖语言的真值规则。

### 案例 6：全量标记漏发脏集 flush

- 提示词（摘要）：test_main 偶尔报 `q_tail != marked`，检查驱动启动全量标记的写法。
- 模型输出：定位到全量标记只写 `CTRL_CLEAR_Q`，给出补 `DIRTY_FLUSH` 的修改。
- 人工修正：要求先写“留两条记录再执行 test_main”的定向用例，修复前必须失败。
- 验证：先留两条记录再执行 test_main，修复前 `q_tail=10 != marked=9`，修复后 ALL PASS
  （tools/logs/board_phase3_leftover.log）。
- 结论：跨进程保留的硬件队列要在每轮启动时显式清空，不能假设调用方已经清理。

## 4. 构建、测试与工具案例

### 案例 7：测试脚本按内容重命名

- 提示词（摘要）：把 gc_test.py、three_way.py、run_test_main.sh 改成“比什么”的名字，
  运行后自动把日志写到 logs/<项目>_<时间>.log。
- 模型输出：批量改名并同步 29 处引用；在三个脚本里加 Tee，把 stdout/stderr 同时写文件。
- 人工修正：改名不彻底。日志前缀仍是 gc_test / three_way；tools/push_tests.ps1 只匹配
  run_*.sh，改名后的包装脚本没有被推上卡；卡上还留着 tests/gc_test.py。
- 验证：板上四个入口各执行一次，退出码全 0，logs/ 下各生成一份日志，推送文件 md5 一致。
- 结论：改名要覆盖四层：文件名、日志前缀、调度脚本的过滤条件、卡上副本。

### 案例 8：重建位流的哈希与发布资产不一致

- 提示词（摘要）：本地重新综合位流并上板验证。
- 模型输出：重建成功，建议把文档里的位流哈希更新为新值。
- 人工否决：布局布线不可比特复现，重建哈希变化是正常现象；发布资产与文档继续引用已发布
  的 6D479244…，重建位流只用于本地验证。
- 验证：重建位流 md5 965B0A2C…，时序为正，板上三项测试通过；发布资产未改动。
- 结论：哈希用于标识发布物，不用于证明“同源代码”。

### 案例 9：Vivado 汇总脚本读数错误

- 提示词（摘要）：从实现报告里提取资源与时序，输出 Markdown 表。
- 模型输出：初版只读出 BRAM 与 DSP，LUT/FF 为空，百分比列也错位。
- 人工修正：报告里同时存在 CLB LUTs 与 Slice LUTs 两类行，必须取后者；百分比在最后一列。
- 验证：修正后读出 LUT 27,192 / FF 71,466 / BRAM 5.5 / DSP 0，WNS/WHS +0.049。
- 结论：报告解析要打印原始行核对，不能以脚本未报错作为结论。

### 案例 10：串口推送脚本无响应

- 提示词（摘要）：把改好的脚本推到板上。
- 模型初判：提示符匹配失败，怀疑终端状态栏重绘干扰正则。
- 人工修正：手工回车能收到提示符，说明链路正常。逐个脚本对照后发现串口公共件与两个推送
  脚本默认 115200，而控制台是 921600。
- 验证：统一默认值后逐文件 md5 MATCH；单命令回显正常。
- 结论：先证明链路通，再怀疑匹配逻辑；默认值不一致会表现为“完全没反应”。

### 案例 11：API 建提交造成假的 ahead/behind

- 提示词（摘要）：git push 被重置，改用 GitHub API 推送。
- 模型输出：用 blob/tree/commit/ref 重建提交并更新分支，内容一致。
- 现象：本地状态显示领先 6、落后 7，但两边树哈希相同（e596dff）。
- 人工修正：根因是 API 重建改变了提交哈希。用 git fetch 加 git reset --keep 对齐本地，
  网络恢复后改回真实 push。
- 验证：对齐后 rev-list 计数为 0 0；随后一次真实 push 成功（44b9c7b）。
- 结论：树相同不等于提交相同；走 API 后必须同步本地引用。

### 案例 12：卡上与远端的旧脚本副本

- 提示词（摘要）：检查仓库和卡上还有没有重复的、没改名的脚本。
- 模型输出：仓库源码已无旧名；重复项都是卡上镜像。
- 人工修正：卡上仍有 tests/gc_test.py；远端分支仍有 run_gc.sh 与 run_repeat.sh——上一轮
  用 API 建树时只能新增，无法表达 git mv 的删除侧。
- 验证：卡上删除旧文件并用 md5 核对新文件；远端提交里显式加入删除项，main 树不再含旧名。
- 结论：重命名要同时检查工作区、索引、远端树、卡上副本四处。

## 5. 被否决或未采用的建议

- 用 PYNQ overlay 包装：本项目对象图驻留 DDR、PS 侧走非缓存映射，接入 PYNQ 需要重做内存
  模型，收益低于成本；改为在报告中说明选择 RTL 加自研驱动的理由。
- 封装 AXI DMA：本项目没有 DMA IP，缓存一致性是“避开”而不是“处理”，写成封装会误导读者。
- 把 main 改成 dev 的镜像分支：main 保持发布树，按版本 squash。
- 用重建位流替换发布哈希：破坏发布物可追溯性，已否决。

## 6. 可复用提示词

- 写 RTL：先给出状态机与握手假设，再写断言和负控，最后才改实现。
- 审查差异：只报告会导致结论变化的问题，按文件与行号给出证据，附最小复现命令。
- 重构测试：先给出“比什么”的命名表与引用清单，再改文件，最后在目标环境重新执行并核对日志名。

### A.2 写 RTL 时的回答节选

- 换图残留：“三个同拍点要一起改：START 只在引擎空闲时下发；数据 FIFO 的弹出与丢弃都用
  run_start/abort 门控；flush 退出条件加 !ARVALID，等已发出的 AR 返回。三个定向
  testbench 做守护。”
- 命令 FIFO：“出队与入队都要加 !run_start && !abort；脉冲结束后断言 c0r==c0w。
  未修复时会看到 c0r=4、c0w=5。”
- 队列满：“入队失败要粘滞到 STATUS[0]；正常负载峰值 4094/4096，只有 force q_full
  能覆盖这个分支。”
- 位图探针：“写 BM_ADDR 后固定等 2 拍再读；地址写后回读校验，失败返回 0xFFFFFFFF，
  调用方退回全量标记。”
- 先断言：“先写 T-ABORT/T-RACE/T-CMDFIFO 的负控，确认去掉修复会失败，再改 RTL。”
