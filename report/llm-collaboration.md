# 大模型协作记录

本文件记录 2026-10 用编码助手（大模型）参与本项目的方式，以及几处模型建议被人工纠正的过程。
记录按案例摘录提示词意图、模型输出、人工修正与验证证据，不逐字复刻对话。

## 1. 使用方式与边界

- 角色：模型负责实现、重构、文档整理与差异审查；人负责需求、验收口径、上板实测与发布决策。
- 约束：仓库内的 AGENTS.md 是协作规范，要求每次改动给出验证命令与结果、禁止用编译或综合
  代替验证、禁止为了通过而放宽测试。
- 记录边界：模型输出不构成证据。所有结论以仓库中的代码、测试、日志与发布资产为准。

## 2. 协作流程

1. 人给出目标与验收标准（例如“测试脚本按比什么重命名，运行时自动写日志”）。
2. 模型提出改动清单与验证命令，先列清单再动手。
3. 模型实现并执行本地检查（契约测试、语法检查、负控）。
4. 人在板上执行，模型根据串口输出修正判断。
5. 双方确认后提交；提交信息必须带 verified / unverified 两行。

## 3. 案例

### 案例 1：测试脚本按内容重命名

- 提示词（摘要）：把 gc_test.py、three_way.py、run_test_main.sh 改成“比什么”的名字，
  运行后自动把日志写到 logs/<项目>_<时间>.log。
- 模型输出：批量改名并同步 29 处引用；在三个脚本里加 Tee，把 stdout/stderr 同时写文件。
- 人工修正：改名不彻底。日志前缀仍是 gc_test / three_way；tools/push_tests.ps1 只匹配
  run_*.sh，改名后的包装脚本根本没被推上卡；卡上还留着 tests/gc_test.py 与旧包装脚本。
- 验证：板上四个入口各执行一次，退出码全 0，logs/ 下各生成一份日志，推送文件 md5 全部一致。
- 结论：改名要覆盖四层——文件名、日志前缀、调度脚本的过滤条件、卡上副本。

### 案例 2：串口推送脚本“没有任何反应”

- 提示词（摘要）：把改好的脚本推到板上。
- 模型初判：提示符匹配失败，怀疑 tmux 状态栏重绘干扰正则。
- 人工修正：手工回车能收到提示符，说明链路正常。逐个脚本对照后发现
  serial-session.ps1 与两个推送脚本默认 115200，而控制台是 921600。
- 验证：统一默认值后 serial_push_chunked.ps1 逐文件 md5 MATCH；serial_cmd.ps1 正常回显。
- 结论：先证明链路通，再怀疑匹配逻辑；默认值不一致会表现为“完全没反应”。

### 案例 3：重建位流的哈希与发布资产不一致

- 提示词（摘要）：本地重新综合位流并上板验证。
- 模型输出：重建成功，建议把文档里的位流哈希更新为新值。
- 人工否决：布局布线不可比特复现，重建哈希变化是正常现象；发布资产与文档必须继续引用
  已发布的 6D479244…，重建位流只用于本地验证。
- 验证：重建位流 md5 965B0A2C…，WNS/WHS 为正，板上三项测试全部通过；发布资产未改动。
- 结论：哈希用于标识发布物，不用于证明“同源代码”。

### 案例 4：API 建提交造成假的 ahead/behind

- 提示词（摘要）：git push 被重置，改用 GitHub API 推送。
- 模型输出：用 blob/tree/commit/ref 重建提交并更新分支，内容一致。
- 现象：本地 git status 显示领先 6、落后 7，但两边树哈希相同（e596dff）。
- 人工修正：根因是 API 重建改变了提交哈希。用 git fetch 加 git reset --keep 对齐本地，
  之后网络恢复时改回真实 push。
- 验证：reset 后 rev-list 计数为 0 0；随后一次真实 push 成功（44b9c7b）。
- 结论：树相同不等于提交相同；走 API 后必须同步本地引用。

### 案例 5：去掉 README 灰色方框后契约测试失败

- 提示词（摘要）：README 里除命令外不要用行内代码，表格也不要。
- 模型输出：批量去掉反引号，表格改为纯文本。
- 现象：契约测试报 4 个参数不一致，VERSION 解析抛异常。
- 人工修正：测试用正则要求反引号包裹数值；把正则改为“反引号可选”，契约本身不变
  （README 仍必须给出参数与版本号）。
- 验证：61/61 通过；另外确认表格里的 0x30/0x34 数值仍能被解析。
- 结论：改展示格式时要同步改解析器，但不能放宽“文档必须给出数值”的契约。

### 案例 6：文档口语化

- 提示词（摘要）：文档不要口语，统一口径，表格列名用名词。
- 模型输出：多轮改写后仍有口语化表达（如“一句话”“看串口日志”）。
- 人工修正：把要求固化为写作规则，逐条给出错误写法与正确写法，并写入 AGENTS.md 的文档
  章节，后续文档统一引用。
- 验证：全文搜索口语词与引用块，清理后重建。
- 结论：口头要求会反复回退，规则要落成文件并挂到协作规范上。

### 案例 7：Vivado 汇总脚本读数错误

- 提示词（摘要）：从实现报告里提取资源与时序，输出 Markdown 表。
- 模型输出：初版只读出 BRAM 与 DSP，LUT/FF 为空，百分比列也错位。
- 人工修正：报告里同时存在 CLB LUTs 与 Slice LUTs 两类行，必须取后者；百分比在最后一列，
  不是第二列。
- 验证：修正后读出 LUT 27,192 / FF 71,466 / BRAM 5.5 / DSP 0，WNS/WHS +0.049。
- 结论：报告解析要打印原始行核对，不能以脚本未报错作为结论。

### 案例 8：卡上与远端的旧脚本副本

- 提示词（摘要）：检查仓库和卡上还有没有重复的、没改名的脚本。
- 模型输出：仓库源码已无旧名；重复项都是卡上镜像。
- 人工修正：卡上仍有 tests/gc_test.py；远端分支仍有 run_gc.sh 与 run_repeat.sh——上一轮
  用 API 建树时只能新增，无法表达 git mv 的删除侧。
- 验证：卡上删除旧文件并用 md5 核对新文件；远端提交里显式加入删除项，main 树不再含旧名。
- 结论：重命名要同时检查“工作区、索引、远端树、卡上副本”四处。

## 4. 被否决或未采用的建议

- 用 PYNQ overlay 包装：本项目对象图驻留 DDR、PS 侧走非缓存映射，接入 PYNQ 需要重做内存
  模型，收益低于成本；改为在报告中说明选择 RTL 加自研驱动的理由。
- 封装 AXI DMA：本项目没有 DMA IP，缓存一致性是“避开”而不是“处理”，写成封装会误导读者。
- 把 main 改成 dev 的镜像分支：main 保持发布树，按版本 squash；分支策略不在本次调整范围。
- 用重建位流替换发布哈希：破坏发布物可追溯性，已否决。

## 5. 可复用提示词

- 整理文档：按“先结论后依据、一句一意、数字可追溯”改写，列出改动清单后再落盘。
- 重构测试：先给出“比什么”的命名表与引用清单，再改文件，最后在目标环境重新执行并核对日志名。
- 审查差异：只报告会导致结论变化的问题，按文件与行号给出证据，附最小复现命令。
